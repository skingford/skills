## 全书论点

模型不是不懂设计，而是**分布收敛**：需求含糊时它采样向训练数据的高频、稳妥处靠拢——无衬线字体、浅色背景配紫色渐变、四平八稳的布局。通用、安全，因此平庸。

> 教会 AI 做设计的，从来不是更强的模型，而是更好的设计师。

解法不是等更强模型，而是把专业判断**显式写出来、注入链路、并沉淀为机制**。人可以把判断留在经验里，Agent 需要判断被写出来。

## 第一章 设计工程（可控的高质量生成）

### 1.1 Design I/O

把生成从黑盒拆成可介入的链路。三个层次：

1. **主链路**：prompt → 理解规划 → 搭骨架 → 填充 → 细化 → 评估 → 原型
2. **token 注入**：颜色/间距/字号不属于单一工序，自搭骨架起**贯穿全局**——视觉一致性不取决于某步做对，而取决于每步都不破坏既有约束
3. **critique 回流**：评估不达标时不从头重来，带着具体问题退回对应环节

链路顺序不可随意：每步以上一步产出为前提，**上游偏差会沿链路放大**，所以约束要尽早进入、每环节持续检查，而非末端补救。

「环节即接口」——每个环节都是可接收设计能力的接口：

| 环节 | 进入的能力 | 约束什么 |
| --- | --- | --- |
| 规划 | spec.md | 功能为谁做、覆盖哪些状态、什么算验收 |
| 搭骨架 | template / design.md | 页面骨架、密度、颜色、间距取值 |
| 填充 | components / domain.md | 能用哪些组件、领域状态与数据表达 |
| 细化 | craft.md / design.md | 动效、工艺细节、视觉状态，不显套路 |
| 评估 | evaluator | 按维度对照标准打分，达标还是回流 |

### 1.2 设计声明与执行契约（全书核心）

分类不是先验设计的，是从反复的生成失败里整理出来的。两类缺口：

- **判断标准缺口** → 设计声明（管方向）：Agent 不知道什么状态/颜色/组件/动效才算对
- **执行路径缺口** → 执行契约（管路径）：标准写在文档里，但 Agent 不知道何时读、怎么用、做完怎么检查

|  | 设计声明 | 执行契约 |
| --- | --- | --- |
| 回答问题 | 什么样的设计是好的 | 怎么把它做出来 |
| 来源 | 生成结果反复错在同一类判断上 | 标准写了，但链路里没人调用 |
| 典型内容 | spec、domain、craft、design.md、components、template | skill、evaluator |
| 缺失后果 | 产物能跑，但判断失准 | 标准很多，但进不了流程 |

#### 六份设计声明

| 生成里暴露的问题 | 声明 | 约束什么 |
| --- | --- | --- |
| 主流程能跑，空态、错误态、权限态消失 | `spec.md` | 功能定义、状态流、边界条件、验收标准 |
| 页面像通用 SaaS，不像云安全/数据库/控制台 | `domain.md` | 领域语义、风险编码、业务操作边界 |
| 功能完整，但一眼是 AI 模板 | `craft.md` | 排版、层级、动效、材质等通用工艺 |
| 色值、字号、圆角、动效散落在代码里 | `design.md` | token、视觉语义、状态派生、系统缺口 |
| 组件看起来像，但语义用错 | `components` | 组件可用范围与语义边界 |
| 页面骨架从零猜，场景结构走偏 | `template` | 页面骨架、app shell、场景结构起点 |

**spec.md 六层**（L5/L6 最常被漏——模型优先完成主流程和成功态，因为那最像一张完整截图）：

| 层 | 回答 |
| --- | --- |
| L1 定位与意图 | 功能是什么、为谁做、到哪为止（含非目标、行为边界：始终/询问后/永不） |
| L2 信息架构 | 屏幕分哪些区域，每区承载什么（含区域边界、内容生长规则） |
| L3 核心链路 | 经过哪些状态，如何流转（状态清单、主链路、分支链路） |
| L4 组件功能细节 | 每个组件在各状态下如何表现 |
| L5 边界条件 | 空、加载、错误、权限不足怎么办 |
| L6 验收标准 | Given/When/Then + 设计完成定义 |

L6 是 evaluator 的接口：评估器能判断达标，是因为 spec 先定义了什么叫达标。
分工细节：spec 只把加载态纳入功能边界（何时进入、能否操作、失败如何恢复）；用骨架屏还是 Loader、等多久才反馈，归 craft。

相关范式 **SDD（Spec-Driven Development）**：OpenAI 的 Sean Grove 在「The New Code」提出，把事实源从代码上移到规格，代码是规格在某次实现里的投影。

**domain.md**：只处理业务语义与责任判断。同一个红色——domain 回答「它代表什么风险」，design.md 回答「它引用哪个 token」，craft.md 回答「它出现得是否克制」。
- 风险等级稳定映射语义 token（`--warning-high` / `--warning-medium` / `--warning-low` / `--unknown`），颜色在云安全语境里是**在编码风险**，不是区分系列
- 不可逆操作（关闭防护、批量删除、解除告警屏蔽）须二次确认，且确认文案写清后果：「关闭后，该资产将不再受 XX 防护」优于「确定吗？」
- 敏感字段（AccessKey、主机 IP、账号）默认脱敏，显式点击才展示明文，明文查看行为需被记录
- 缺 domain，Agent 会做出「换个产品也成立」的页面：把危险操作做轻、把敏感信息做明

**craft.md**：跨业务的通用工艺，不定义业务语义、不维护 token。按层组织（基调身份/色彩材质/几何空间/字体排版/图表数据/状态反馈/动效可访问性）。规则须满足三点：**现象可观察、执行动作明确、结果可验收**。

**design.md 七层**（token 只覆盖 V3 和部分 V4，真正让系统成立的是 V1→V7 的连续关系）：

| 层 | 定义 | 防止 |
| --- | --- | --- |
| V1 视觉意图 | 品牌气质、视觉密度、中性色温、语言优先级 | 只知道色值，不知道页面该给人什么感觉 |
| V2 视觉角色 | CTA、链接、软底面、边框、图表色、状态色各自职责 | 颜色只是装饰，无法稳定表达层级与动作 |
| V3 视觉值系统 | color/typography/layout/spacing/shape/elevation/motion/z-index/明暗 | `#fff`、`13px`、`200ms` 散落在实现里 |
| V4 派生机制 | brand 色阶、density 几何、状态变体、明暗映射 | 每个状态新造一个值，系统无法联动 |
| V5 组件视觉属性/状态/响应式 | 各态视觉、breakpoint、touch target | 焦点态、触达面积、断点被漏掉 |
| V6 图形、数据视觉与典型表面 | 图标、插画、图表、空态图、modal/toast/table cell | 图形资产与常见表面不像一个系统 |
| V7 执行与缺口 | `var(--*)`、lint、`gaps.log`、fallback、拒绝生成边界 | Agent 私自绕过规范，缺口被藏进代码 |

V3 值的三档管理：
```
⚠️ 必填：brand、background、foreground、primary、chart-1..12
🟡 可调：radius、font-cn / font-en、状态色
🔒 勿改：duration、ease、z-index、leading   ← 人因学底线，不因「想活泼点」而改
```

V4 派生（没有派生机制，Agent 会在每个状态里重新发明一个值）：
```
brand hex → 50-950 色阶 → brand / hover / active / surface / border
density → radius / space / control-h
neutral temp → background / foreground / card / border
base token → hover / active / disabled / selected
```

V5 焦点态不可省：`outline: 2px solid var(--ring); outline-offset: 2px;`，不可降级为 `outline: none`——模型很容易为了「干净」删掉它，声明要写死这条底线。

V7 执行约束收成三件事：
```
1. 所有视觉值走 var(--*) 引用
2. hover / active / disabled / selected 从基础 token 派生
3. 找不到 token，不硬写字面量，记录到 gaps.log
```

**gaps.log / 合法失败（Legible Failure）**——最容易被低估的机制。它记录的不是失败，而是**真实的系统缺口**：
```
2026-05-06 [low] warm skill 要求的 aurora 背景 hex (#FFE4C4 等) 不在 token -- fallback: 不加 aurora，纯白 bg-background；视觉略平
2026-05-06 [med] transform scale 因子 (active:scale-0.97 / hover:scale-1.02) 无 token -- fallback: Tailwind arbitrary [0.97]，违反 design.md 执行约束 §1 但无替代
```
有合理替代 → 采用 fallback 并记录；没有 → **拒绝生成那一部分**，等待补 token。比起悄悄写一个 `#FFE4C4`，明示缺口更有价值，因为它会进入下一轮设计系统迭代。

**components**：登记组件与其**语义边界**，重点不是「有哪些组件」，而是「在这套产品语言里这个组件意味着什么」。四层：组件来源 / 语义角色 / 变体与状态 / 组合边界。

| 组件对 | 看起来像 | 真正差别 |
| --- | --- | --- |
| Badge / Tag | 都是小标签 | Badge 偏附着、状态、计数；Tag 偏分类、可选、可移除 |
| Modal / Dialog / Drawer | 都是弹出层 | 打断程度、信息密度、退出方式不同 |
| Tabs / Tabs-Switch | 都能切换 | Tabs 管同空间视图切换；Tabs-Switch 管模式或口径切换 |
| Dropdown / Menu / Command | 都是浮层列表 | Dropdown 局部选择；Menu 动作集合；Command 搜索式操作入口 |

示例：资产列表里「运行中」「高危」「ECS」「生产环境」都是短文本，但责任不同——状态、风险、资源类型、业务分类。全做成同一种 Badge，视觉整齐，语义被抹平。
单个误用未必出事，误用积累起来整套交互语法会变含混，用户每次看到组件都要重新猜它意味着什么。

**template**：管「像哪类页面」，不管「这次页面具体写什么」。四层：场景 / 骨架 / 密度 / 禁用边界。
坑：CloudAI 和 data-agent 都有同名 `custom-agent-list.tsx`，但结构不同（前者通用 grid，后者带发布状态 tabs）——**文件名相同不代表场景相同**。`sample-*.tsx` 只供视觉参考，不是可复用骨架。

#### 两份执行契约

**skill（调度契约）**——把能力封装成可调度单元，不另起一套审美，只在正确时机读取、组合、执行声明。四层：

| 层 | 解决 |
| --- | --- |
| 触发条件 | Agent 怎么知道该读它（description 本身就是触发信号） |
| 能力主体 | 这件事按什么步骤做（如 cloudai-picker 的五步：定主题→命中场景→布局级决策→选组件→报告决策待确认） |
| 分层引用 | 细节很多时哪些内容按需进上下文（控制声明进入链路的**节奏**；一次塞 30+ 模版会淹没注意力） |
| 坑位沉淀 | 已犯过的错怎样避免再犯 |

调度到位后，用户只说一句话，无需喊「现在该用 X 了」：需求内容 + skill 触发条件 + 链路调度位置共同决定能力何时出场。

**evaluator（验收契约）**——不重新发明标准，只把声明转成检查项，并把问题**回指到对应声明**。skill 守入口，evaluator 守出口。

### 1.3 实操：一句话到一个页面

五步：理解/规划（产出六层 spec；视觉方向未沉淀时同步定 visual-spec，否则模型会先用默认视觉补位并带进后续）→ 信息架构（可用 variant skill 生成「总览优先/列表优先/异常优先」等 IA 变体，差异不在视觉而在注意力先给谁）→ 组件设计（把信息映射到正确组件语义，不是把槽位填满）→ 交互设计（补非理想状态）→ 评估。

**回流索引**（不满意时不要在整页反复打补丁，先判断问题属于哪类）：

| 看到的问题 | 回到哪里 |
| --- | --- |
| 主流程能跑，但空态、失败、权限态缺失 | `spec.md` |
| 页面不像这个业务 | `domain.md` |
| 页面有 AI 味 | `craft.md` |
| 色值、字号、动效时长写散了 | `design.md` |
| Badge/Tag、Dialog/Drawer 混用 | `components` |
| 页面结构像卡片墙，不像看板 | `template` |
| 评估说不清哪里错 | `evaluator` |

两条交付路线：**直接交付**（结构明确、规则已沉淀 → 声明与契约直接生成 prototype）；**Figma 增强**（视觉复杂度高、需继续推敲 → 主链路上接 Figma MCP 画完再回写 IDE）。Figma 不是这套能力成立的前提，是复杂场景下对主链路的补充。

## 第二章 动态交互（体验随意图被实时组织）

### 2.1 从 UX 到 AX

UX 帮用户把目标转成系统操作，解决**执行鸿沟**。但复杂系统里用户仍会停在目标面前不知点哪。Agent 成熟后：用户先表达意图，Agent 理解目标、补上下文、推进任务。

> UX made complex systems usable by improving the journeys people navigate. AX removes the journey altogether, teleporting people directly to their goals. —— John Maeda

关键转折：执行鸿沟被压缩后，**评估鸿沟变得更突出**——用户没亲手做每一步，更需要知道 Agent 做了什么、为什么、哪里不确定、出错能否撤销。

|  | UX | AX |
| --- | --- | --- |
| 设计对象 | 用户如何理解并操作界面 | 用户如何委托、验证并修正 Agent 的行动 |
| 主要挑战 | 降低认知与操作成本 | 压缩执行鸿沟，并处理被放大的评估鸿沟 |
| 界面职责 | 呈现入口、路径、控件、反馈 | 承接意图表达、过程协作、证据解释、结果评估 |

过程透明度**并非越高越好**：Agent 中间信息全平铺给用户，透明度本身变成信息负担。应按任务阶段、风险等级和用户决策需要动态调节暴露层级。

UX 与 AX 不是替代关系：稳定仪表盘、固定设置页、重复审批流仍适合预先设计成页面。

### 2.2 GenUI

GenUI 不是「生成页面」，而是定义设计规则，把数据、上下文和组件**编排**成体验。

边界：只在**任务路径、判断依据或用户决策点会变化**的地方引入 GenUI。稳定页面仍然重要，不需要为了「生成」而被重新生成。

两个判断维度：**表达自由度**（自由度低→一致性好但覆盖有限；高→适应性强但安全/性能/品牌一致性变难）与**产品控制权**。
结论：**受控生成**更可靠——Agent 输出结构化意图或界面描述，客户端用组件目录、渲染规则和交互约束组织界面。GenUI 追求的不是无限自由，而是**有边界的灵活性**。

### 2.3 A2UI

Agent to UI：Agent 用结构化方式声明界面意图，客户端用受控组件、设计系统和交互规则完成渲染。**不是让模型自由编写 HTML/CSS**。

契约把「要表达什么」和「如何渲染」分开。Agent 声明 intent/status、context、content、actions、behavior（`requires_user_decision`、`blocks_agent_execution`）；客户端选组件、上 token、守无障碍与降级。字段可随实现变化，但这条分工必须稳定。

用户操作会带着上下文**传回 Agent**——界面不只展示结果，也把用户判断重新写回任务上下文。

### 2.4 案例

OmniBox（承接意图：自然语言 + 数据范围 + 知识库 + 指标对象 + 历史上下文 → 可执行任务上下文）→ FlexCard（承接过程协作：分析方向选择、高权限查询授权，用户确认前暂停执行）→ GenReport（承接结果评估：Artifacts 形态，需声明式规则约束——哪些指标必须出现、图表如何绑定数据、洞察必须引用哪些证据）。

一个面向 Agent 的产品不需要把所有页面都生成出来，而要识别**哪些时刻**会因意图、上下文、数据和决策变化而需要动态界面。

## 第三章 自我进化（从人工指正到评审运行时）

### 3.1 人工指正的尽头

人看的上限：质量取决于那个人愿意看多少遍、能否稳定说出为什么不对。而很多指正并不新鲜——「第一屏看不出主任务」「卡片节奏太平均」「像通用模板」会在不同项目里反复说。**它们是稳定判断，应该被沉淀**。

自我进化不是让 AI 自己宣布自己变好，而是把稳定判断变成可运行的评审循环：生成器提出原型 → 评估器判断 → 达标则输出，不达标输出优化指令回流。

人的位置变了：不再在每轮循环里反复指出同类问题，而是进入上游——修订 framework、prompt、schema、policy，把稳定判断写成运行时能执行的契约。

**分数只是外显结果，真正重要的是分数背后的证据链和回流路径。**没有证据链，AI 容易把完整度误当质量；没有回流路径，评估只是事后报告。

### 3.2 评估标准：页面类型 + 六维度

同样是 UI，失败方式不同。先判断 page shape，再用同一组六维度评估，**只是权重不同**——既保留差异，也保留共同语言。

| 页面类型 | 任务 | 主任务 | 典型失败 |
| --- | --- | --- | --- |
| Brand Landing Page | 转化型 | 把注意力转成兴趣与信任 | 通用模板、品牌记忆弱、承诺含混 |
| Product Console | 任务型 | 帮用户安全完成操作任务 | 主任务不清、状态断裂、信息密而无用 |
| Conversational Interface | 任务型 | 帮用户通过对话提问、判断、恢复 | 轮次状态不清、回答无依据、缺少恢复 |
| Data Dashboard | 判断型 | 帮用户判断状态并诊断变化 | 装饰大于含义、指标层级弱 |
| Content / Documentation | 判断型 | 帮用户找到并应用知识 | 难扫描、结构弱、声明无证据 |

用户提供明确任务时它是权威输入；没有任务时，prepare 阶段从产物的 title、h1、导航、链接、可见文案、图片和结构推断临时目标，标记 `inferred_from_artifact`。这一步解决「用错尺子」：没有 brief 的品牌首页不该被评成缺少下单系统。

六维度从三类真实业务关注拆出（业务语义层 / 用户任务层 / 界面实现层）：

| 维度 | 中文 | 评审关注 |
| --- | --- | --- |
| Product Intent | 产品意图 | 价值主张、目标用户、主任务、内容语气、CTA 是否匹配真实目标 |
| Trust & Domain Fit | 业务可信 | 领域术语、数据声明、风险权限、合规、AI 置信与证据 |
| Information Architecture | 信息架构 | 层级、分组、导航顺序、密度、节奏是否服务扫描与决策 |
| Interaction Readiness | 交互就绪 | 控件可理解、动作有反馈、关键路径可完成可恢复 |
| System Craft | 系统工艺 | 字体、间距、圆角、阴影、组件、状态、桌面布局是否像一套系统 |
| Visual & Brand Expression | 视觉品牌 | 色彩、字重、图像、动效是否形成适合品类的品牌表达 |

**权重表**（同一维度在不同页面里重心不同——好设计不是同一种「好看」）：

| 维度 | Brand Landing | Product Console | Conversational | Data Dashboard | Content/Doc |
| --- | ---: | ---: | ---: | ---: | ---: |
| Visual & Brand Expression | 25% | 8% | 8% | 8% | 8% |
| Product Intent | 20% | 22% | 18% | 18% | 18% |
| Information Architecture | 18% | 22% | 16% | 24% | 28% |
| System Craft | 15% | 14% | 12% | 16% | 14% |
| Trust & Domain Fit | 12% | 18% | 22% | 22% | 22% |
| Interaction Readiness | 10% | 16% | 24% | 12% | 10% |

**subcheck 让维度可追账**，0-2 分：2=pass（基本满足，轻微修整）/ 1=partial（弱点已影响质量）/ 0=fail 或 critical_fail（进入阻断判断）。

```
dimension_score = sum(subcheck.score) / sum(subcheck.max_score) * 10
```

这条公式把 evaluator 从印象打分推向证据打分：**不能先写一个分数再补一句解释**，必须先检查每个 subcheck、记录证据与扣分原因，再向上聚合。分数要能反推。

### 3.3 证据链

evaluator 不是「让模型看一段 HTML 然后打分」，而是**一套完整评估运行时**：先多模态收集证据，再交评审模型，最后由运行时重新算账、处理阻断、生成报告。

「像人一样评估」不是让 AI 凭感觉替代设计师，而是让它先获得**接近真实评审者的证据条件**：页面真的被打开过、画面真的被截图过、关键控件真的被点击过。

**Evaluator 面对的是交付物，不是生成器的意图。**

四层证据：

| 证据层 | 内容 |
| --- | --- |
| DOM / CSS QA | 横向溢出、文字裁切、低对比度、fixed 溢出、小点击目标、交互元素缺少名称、图片损坏 |
| Page Profile | section、图片、链接、真实路径、占位链接、导航文案、headline、CTA、可点击目标 |
| Click Smoke | 点击可见目标后是否出现 console error、page error、broken image、dialog 或无反馈 |
| Screenshot | 桌面端截图与 full-page 截图，供 visual review 与报告引用 |

默认视口桌面 `1440x1000`，且 prompt 明确要求**不因缺少移动端截图而扣分**（边界清楚，评审才不会在证据之外乱扣）。运行时阻断外部字体依赖，减少网络字体的非确定性——同一原型每次打开字体都不同，截图判断就成了偶然。

**浏览器 QA 是事实层，不是评分层**：它能说页面是否溢出、图片是否断、点击是否报错；不能判断落地页有无品牌记忆。一个页面可以没有 critical QA 但仍然很弱。三者不能互相替代：浏览器把问题变成事实，评审模型解释事实对设计质量的影响，运行时把解释落回分数、阻断项和报告。

**截图补 DOM 看不到的问题**——DOM 完整不等于用户看到的页面成立（标题存在于 DOM 但被背景吃掉；元素完整但截图里有空洞）。五类截图判断：text_readability、visual_hierarchy、composition_risk、brand_tone_fit、motion_purpose。

> **DOM/CSS 检查与截图观察冲突时，截图证据优先。**用户不会看到 DOM 说自己没问题，用户看到的是画面。

这是对 AI 生成 UI 的必要校准：AI 很擅长生成「结构完整」的页面，但结构完整经常只是看上去有东西。

输出结构约束（`evaluation-output.schema.json`）：每维度须含 `dimension`/`score`/`subchecks`/`evidence`/`why_not_higher`/`recommendation`；每检查项须含 `id`/`label`/`score`/`max_score`/`verdict`/`evidence`/`deduction_reason`/`recommendation`。

**模型总分只是建议**，最终分数由运行时按六维、检查项分数和页面类型权重**重新计算**——模型判断「为什么」，但交付裁决不完全交给一次语言输出。

### 3.4 交付闸门

平均分会掩盖致命问题。闸门回答的不是「这一版几分」，而是「能不能进入下一步」。

**评审模式表达产物成熟度**（模式不改变评分模型，只改变放行策略）：

| 模式 | 阶段 | 阈值 | 策略 |
| --- | --- | ---: | --- |
| `vibe_draft` 过程稿 | 方向探索 | 7.5 | 先看方向、意图、IA、品牌与工艺；后端、路由、占位链接多为提示 |
| `prototype` 原型 | 路径演示 | 8.0 | 不要求真实后端，但主路径应有可见模拟状态；交互问题影响通过 |
| `release_gate` 上线门禁 | 交付验收 | 8.0 | 要求生产化路径、导航、数据与关键状态；占位路径可能阻断 |

同一个问题在不同阶段严重度不同：过程稿里「缺真实商品路径」可留作提示，到上线门禁就不能再被解释成「后续会接」。

**阻断问题**（不能被平均分摊薄的失败）：
`unclear_primary_task`（用户看不出要做什么）、`critical_rendering_failure`、`hero_primary_copy_unreadable`、`primary_visual_blocks_information`、`wrong_domain_logic`、`broken_key_task_path`、`operation_flow_has_dead_end`、`disconnected_controls_or_states`、`broken_conversation_flow`、`untrustworthy_ai_response`、`brand_tone_mismatch`、`placeholder_or_missing_conversion_paths`、`generic_template_output`（页面可以属于任何产品）、`inconsistent_design_system`、`subcheck_evidence_missing`、`screenshot_review_missing`、`critical_subcheck_failure`

> 普通评分器说「这一版 7.8 分」。交付闸门还要说「即使 7.8，它也因为主路径断裂不能通过」。

**优化指令要压缩**，不是愿望清单。反例：「继续优化视觉、增强交互、丰富内容。」正例：「第一屏价值主张在桌面截图中被产品图遮挡，影响产品意图与视觉品牌；先调整标题层级、图文关系和 CTA 位置。主 CTA 点击后没有可见状态反馈，在原型评审模式下影响交互就绪度；下一轮需提供弹窗、抽屉、局部状态或模拟路径。」前者仍需人解释，后者可直接进入生成器输入。

**停止规则**：达阈值且无阻断 → 通过；达最大轮数 → 停；连续多轮标准差很小且最佳分提升有限 → 平台期；连续修订导致分数明显下降 → 返回之前更好的版本。
> 自我进化不是无限迭代。能停，也是能力的一部分。

### 3.5 工程化与标准维护

**隔离系统保护评审对象**：生成器与评估器分离，否则评审被「意图」污染。
- evaluator **可读**：任务目标、页面原型、运行截图、浏览器检查、交互路径、六维模型、权重、上一轮评估结果
- evaluator **不可读**：生成器提示词、隐藏规划、私有推理、作者事后解释、无关项目历史

> 生成器可能计划了完整链路，但页面里只有占位按钮；评估器应按占位按钮处理。
> **评审看的是稿件，不是作者脑中的稿件。**

**报告契约**五层：放行结论（分数/阈值/模式/通过或退回原因）、六维度评分、证据解释、阻断问题、优化指令。报告须中文优先，内部枚举留在结构化数据里，正文说「过程稿评审」而非暴露字段名。

**标准维护发生在运行时之外**：用五类样本持续校准——好案例（保护标准不过严）、坏案例（检查阻断能否被识别）、混合案例（局部出色但主路径失败，校准平均分与放行的关系）、边界案例（接近阈值，观察权重稳定性）、品类案例。
每次标准更新要回答四问：是否减少误放行、是否造成新的误退回、是否让某类页面被过度惩罚、是否只修好一个样本却伤害其他样本。

> 标准不是一次写完的。标准是在案例里长出来的。
> AI 不是因为多跑几轮就会变好。它需要一套会看、会判、会回流、会校准的系统。

---

## 结语要点

设计专业如何进入系统：过去判断停在设计师脑子里，以评审意见、口头提醒、Figma 标注或返工的形式存在——人能理解，Agent 不能稳定继承。

把判断拆开、写清、放进链路，「好设计」才从经验判断变成**可被引用、被执行、被追责的系统能力**；一个团队的 taste 也不再只是少数人临场把关，而成为系统持续调用的能力。

这不会让设计变机械，恰恰让最难复制的部分变清楚：判断、取舍、尺度、语气、信任感。**没有人的判断，系统只会更快地产生平均答案。**

> Intent becomes form.
